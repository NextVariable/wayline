# Wayline V0.3 第二阶段验收

基线是公开仓库 main 的 b34eb15。本地 main 比远程少四个提交，V0.3 第一阶段的工作区与远程一致。本轮在独立检出中进行，基线 lint、707 项测试和生产构建通过。第一阶段的地图首屏连接、拒绝后重连、手选日历、失败后保留旧快照、合法空结果及路线恢复均在本轮回归或隔离浏览器中复核。

## 问题与修复

| 严重度 | 问题及处理 | 文件 |
| --- | --- | --- |
| P1 | 日历回调等待账号校验时，同一个 state 可能由两个请求同时处理。授权状态消费前再次核对，回调限制为配置的精确路径与 GET，登录与日历回调配置拒绝查询串和片段。登录需要 Google 返回已验证邮箱。 | `server/google-calendar.mjs`、`server/accounts.mjs` |
| P1 | Google 以 HTTP 403 报告限额时，旧逻辑提示重新授权。现在区分额度与权限问题，保留上次快照。重启后的快照和撤权状态走实际临时加密存储回归。 | `server/google-calendar.mjs` |
| P1 | 模糊文本和部分同名分支可能被供应商返回为唯一精确名称。现在要求足够明确的名称和同城证据，有分支竞争或通用名称时交给用户确认。完整门牌可用同城的精确地址匹配，旧自动查询缓存失效。已经保存到日程的历史点位仍待逐批复核。 | `server/calendar-places.mjs` |
| P1 | 预览访问表单依赖代理转发的 Host，且访问 Cookie 可能在 OAuth 顶层返回时丢失。现在按公开 Origin 严格校验访问表单，HTTPS Cookie 使用 Secure、HttpOnly 和 SameSite=Lax，拒绝的 API 响应不缓存。 | `server/web-host.mjs`、`server/index.mjs` |
| P1 | 路线接口失败后，恢复网络仍需手动重试。当天路线和出差路线均在浏览器恢复联网时恢复查询。 | `src/lib/useTodayLegs.ts`、`src/components/BusinessTripCommute.tsx` |

账号仍以 Google `sub` 隔离，Calendar 的主日历标识与登录邮箱只用于核对这次连接的归属。Google 文档说主日历标识通常与邮箱相同。遇到不一致时仍明确拒绝，转移域名、邮箱别名和 Workspace 管理限制需要真实测试。登录、Calendar 和 Gmail 授权范围沿用原配置。[Google 身份字段](https://developers.google.com/identity/openid-connect/reference) · [Google 日历标识](https://developers.google.com/workspace/calendar/api/concepts/events-calendars)

## 地点识别评测

用 120 条逐条带期望值的合成样本，经前端地点计划、服务端匹配、前端落图判定。供应商响应包含同名分部、遮蔽城市、门牌简写、无结果和服务故障。样本中的名称、地点和坐标均为测试数据，结果衡量规则在受控响应下的行为。待确认表示供应商有候选且系统拒绝自动选点，失败包括无候选和供应商不可用。以下四项比例以 100 条实体地点为分母，另外 20 条线上或空地址单独统计。

| 指标 | V0.3 第一阶段 | V0.3 第二阶段 |
| --- | ---: | ---: |
| 正确自动落图 | 36% | 46% |
| 错误自动落图 | 30% | 0% |
| 待确认 | 28% | 48% |
| 失败 | 6% | 6% |
| 正确跳过的线上或无地址事件 | 20/20 | 20/20 |

第二阶段的 46 个正确点来自标准地址 18 个、公司和园区 16 个、跨城市地址 12 个。重名地点和模糊会议地点各 20 条全部待确认。跨城另外 8 条因供应商城市与文字城市不符而待确认。6 条失败由 4 条模拟供给故障和 2 条无候选构成。

数据在 `tests/fixtures/calendar-place-evaluation.json`。运行 `npx --no-install vitest run --silent=false src/tests/calendarPlaceEvaluation.test.ts` 打印分组结果。复算基线时，将 `WAYLINE_BASELINE_RESOLVER` 指向第一阶段检出的 `server/calendar-places.mjs`。

## 正式环境待验收步骤

1. 准备独立 HTTPS 预发布域名与测试用 Google Cloud 项目。服务端设置 `PUBLIC_ORIGIN=https://<测试域名>`，使用专用凭证和独立私有目录，登记 `/api/auth/google/callback` 与 `/api/calendar/google/callback` 两个完整返回地址。用个人 Google 测试号和 Workspace 测试号分别验证登录、拒绝授权、重新连接、选主日历及共享历。Workspace 额外检查管理员允许策略、主地址和别名行为。
2. 在两个独立浏览器资料夹比较日历和工作区。每个测试账号仅使用事先准备的合成活动，切换账号时检查对方日程不可见。在 Google 账号连接管理撤销测试应用授权，等待一次同步或点「立即同步」，检查提示重新授权且保留旧快照，重连后再确认同步。
3. 用测试代理验证访问日志和缓存。用虚构标记代替真实授权码发送一次回调请求，在代理与应用日志中检查仅记录路由路径，查询串、Authorization、Cookie 和响应正文不进入日志。查看响应头，确认 OAuth Cookie 的 Secure、HttpOnly 与 SameSite 属性，以及 API 的 no-store。确保代理使用固定可信的公开 Origin 和访问来源配置。将凭证目录和静态目录分开，按现有开发文档管理环境变量。
4. 在预发布环境重启实例，验证加密文件及对应密钥挂载后仍可读取测试快照，随后验证令牌刷新。若启用了访问密码，进程重启后的临时预览 Cookie 需要重新签发。测试实际高德查询时使用公开设施地址，记录同名地点、园区和跨城的自动准确率。
5. 用 iPhone Safari 与 Android Chrome 真机各验证地图应用已安装及未安装的场景。打开选定通勤段，跳转、系统返回、刷新、从后台重新进入，再关开网络记录恢复。检查选中态、地图范围及 VoiceOver/TalkBack 的可操作性。

下一轮优先完成正式环境的双账号、撤权、代理与真机验收。第二优先是以真实公开 POI 测量供应商结果，并设计历史自动点位的安全复核。第三优先是记录授权返回至首次上图耗时与失败原因。
