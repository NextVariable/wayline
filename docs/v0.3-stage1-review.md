# V0.3 第一阶段验收

基于公开仓库 main 的 86ad231。开始前，lint、699 项测试和生产构建通过。本地公开版 main 落后远程 3 个提交，本轮基于与远程一致的 V0.2 快照单独检出。测试使用隔离存储和合成账号、日历、地点及路线。

## 核心流程

| 场景 | 改动与边界 |
| --- | --- |
| 首次使用 | 从地图首屏登录、连接日历。授权返回地图后，主日历显示为默认推荐；只有唯一一本时推荐该日历。其他日历可以展开选择。用户确认提交后才读取事件。 |
| 同步状态 | 首次同步中、已同步、空结果及失败各有状态。失败可重试。只有完成的已选日历快照才覆盖现有 Google 日程，合法空结果仍会清除对应日程。 |
| 账号归属 | 已登录空间检查主日历标识与登录邮箱一致，OAuth 请求带账号提示，权限范围沿用只读。旧连接若不匹配，返回重连状态并禁止手动同步。客户端按所有者读取日历和路线状态。 |
| 已知风险和缺口 | 未匹配地点可进入角落提示纠正，候选带城市和地址。日历状态异常时保留已有记录，暂停显示受影响的准时判断。路线响应须与请求的交通方式一致且只包含一段有效路线。 |
| 导航返回 | 今天的地图按工作区保留路线焦点和交通方式。手机同页导航后，一趟出差可从标签页会话恢复已选行程和路段，重新查询路线。 |

## 修改文件

- `server/google-calendar.mjs` 验证账号归属，防止返回不匹配的旧服务端快照，并保留原有只读权限。
- `src/App.tsx`、`src/components/GoogleCalendarConnection.tsx`、`src/lib/useGoogleCalendar.ts` 接通首屏入口、日历选择和同步状态，校验快照是否已经完成。
- `src/lib/calendarPlaces.ts`、`src/components/CalendarPlaceHint.tsx` 改善未定位日程可发现性，区分歧义、查询失败和无匹配。
- `src/lib/useTodayLegs.ts`、`src/components/TodayPanel.tsx`、`src/components/BusinessTripCommute.tsx` 校验路线证据、保留导航状态，补充必要的状态提示。
- `src/styles/globals.css` 调整移动端触点与地点搜索输入。
- 测试覆盖只读 OAuth、账号归属、首次同步状态、空日历、多日历、异常路线和地点纠错。跨时区复验 UTC 查询与全天事件用例。

## 正式 HTTPS 环境待验收

1. 在隔离的 HTTPS 测试域名登记现有登录与日历回调。用两个 Google 测试账号验证首次授权、拒绝、选主日历、选共享工作日历、撤权重连、登录账号切换和后台同步。测试授权和页面设置需要对应测试账号与测试域名。
2. 实验环境仍需核实 Secure Cookie、反向代理和服务日志。检查访问日志是否过滤 OAuth 回调查询串，请求头和路由查询凭证是否脱敏，凭证目录是否在静态根目录之外；验证加密文件及密钥在重启后可恢复。代码检查覆盖 PKCE、浏览器绑定 state、会话权限、加密存储和 API 响应。
3. 使用配置了高德的测试环境检查实际地图、公交和驾车耗时、非私人地址的正确匹配与限流后的恢复。高德的查询时间作为参考，现场路况会变化。
4. 在 iOS Safari 和 Android Chrome 测试已安装与未安装 Amap/Google Maps 的情况，检查实际系统 App 跳转、返回后路线位置与交通方式、VoiceOver/TalkBack。
5. 保留旧工作区数据。历史上已经写入本地或云端备份的来源不匹配记录需要人工核对。本阶段没有执行迁移或重写用户数据。

下一阶段先完成同一套测试账号和手机验收，再用匿名样本量化重名场地、园区地址和跨城地点的正确率，最后测授权成功到日程上图的耗时。

## 最终回归

- lint、75 个文件共 707 项测试、TypeScript 和生产构建通过。洛杉矶时区额外运行地点和 Google 服务端的 35 项用例。
- Chrome 实际打开生产构建，使用 1440px 桌面和 iPhone 13、Pixel 7 模拟配置。覆盖模拟 Google 登录、拒绝后重新授权、键盘确认主日历、手机改选共享日历、首次同步失败重试、候选地点纠错、路线故障重试、公交改打车后风险更新、错误同步时暂停判断、空快照移除路线。测量了手机导航触点以及页面的横向溢出。
- 手机模拟中打开了高德导航链接的替身页面。返回后验收当天交通方式与路段焦点，另外从出差页验收了已选出差和驾车路线的恢复。OAuth、地图瓦片和线路供应使用隔离响应。
